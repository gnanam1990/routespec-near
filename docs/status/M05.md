## What each owned test exercises (real vs simulated)

- **Real:** the installed subject is a separately launched Node process running the exact pinned
  official SDK with the RouteSpec adapter on the SDK's own axios instance. Two builds exist:
  `baseline-client.ts` (resubmits, never reconciles) and `corrected-client.ts` (never resubmits an
  unknown commit; reconciles read-only until terminal). Each build's artifact digest is the SHA-256
  of its own source bytes. All traffic goes through the real loopback proxy, case supervisor,
  journal, and M03 runtime; verdicts come only from the M04 kernel over the journal snapshot.
- **Simulated:** provider behavior and ground truth come from the networkless scenario runtime
  (SIMULATE mode), as the product design requires. The issue-383 and issue-384 cases are
  source-derived scenarios, not reproductions of the real incidents.
- **T-029:** the baseline build fails the issue-383-derived case (kernel REVIEW,
  `INV03_RECONCILIATION_INCOMPLETE`; its resubmission was refused by the fenced journal). The
  capture takes only a case run ID, binds build/artifact/gate/case/session/scenario/manifest/
  policy/adapter/epoch, and walks CAPTURED_UNTRUSTED -> QUARANTINED -> SANITIZED (audited). Capture
  of an open case, premature promotion, review before replay, partial review, and review without
  confirmation are refused. A secret-bearing file is REJECTED and a whole-database text scan finds
  neither the configured secret nor the bearer value. Reordered, placeholder-material, and
  identity-mismatched files stay blocked. A forged copy is recorded as a USER_FILE; journal-level
  rewrites of sanitized content or origin fail; a late journal write after capture makes promotion
  fail with `RS_IMPORT_CAPTURE_MISMATCH` and leaves the corpus count unchanged. Diverging
  timelines and rewritten run-operation lineage are refused.
- **T-030:** an issue-384-shaped user trace (public origin debit, provider-reported SUCCESS,
  private credit, contradictory reporter claim). Nine mappings that would declare ground truth,
  upgrade visibility, weaken evidence limits, claim reproduction, or upgrade coverage are refused
  with specific codes. The ambiguity case is replay-verified (including a separate-process trial),
  reviewed, and promoted. The corrected client then runs both the promoted case and the encoded
  issue-384 scenario: kernel REVIEW, INV-05 `INV05_LEG_NOT_VISIBLE` with reason `NOT_VISIBLE`,
  credit evidence `UNKNOWN`/`PRIVATE_NOT_VISIBLE`, no FAIL.
- **T-031:** a drifting trial blocks verification; a commit retry under a wall-clock timer yields
  `REPLAY_NONCANONICAL_TIMER`; a timeline serving FAILED where the trace saw SUCCESS is
  `MISMATCH`. Four trials (three in-process, one separate process) and a second verification after
  re-mapping all share one canonical digest. Promotion creates a new REVIEWED scenario revision
  (`ISSUE_DERIVED_NOT_REPRODUCED`) and a new corpus (base cases + promoted case, PROMOTION_INTO
  lineage); the base corpus is byte-identical afterwards; a second promotion is refused; the stored
  scenario recompiles to the same digest. Lineage stays `PROMOTED_AWAITING_CORRECTED_RUN`. The
  baseline build still fails both cases of the new corpus (REVIEW). The corrected build, in a new
  gate run bound to the new corpus, passes both cases (`RECONCILED`, terminal REFUNDED, no
  destination credit, `INV03_RECONCILED_WITHOUT_SECOND_MUTATION`), cases are COMPLETED/PASS, the
  gate-level combination of the exact case verdicts is PASS, and lineage becomes
  `CORRECTED_RUN_PASSED`.
- **T-032 / T-033:** explicit revision and promotion after corpus creation leave the original
  corpus, its gate run, and its case runs unchanged; new identities carry typed lineage; the new
  gate run binds the new corpus and its exact revisions; corpus rows and gate corpus bindings are
  immutable; re-using an identity as a revision is refused. Nine corpus variants have nine
  distinct digests with the expected visible diffs; gate-run and kernel evaluation identities
  change with the corpus revision.
- **T-039:** HTML, script, SVG handler, terminal/OSC escapes, bidi override, Markdown links, a
  bare URL, and instruction text are imported under the network tripwire (0 network attempts,
  0 DNS). Every class is flagged (category/path only); persisted text has no markup delimiters,
  control or bidi characters; instruction text changes no state; documents carrying `policy`,
  `verdict`, or `review` fields are rejected by the closed schema.

## Red / green evidence (honest account)

Product code was written before most test files in this stage. Red evidence is the first runs and
a mutation pass.

First runs that failed, and why:

- T-029 first run: 5 of 7 failed on two real product defects. (1) The trace identity schema
  rejected the adapter revision `routespec-adapter@1.0.0` (no `@` allowed), so every installed
  capture was REJECTED as `IDENTITY_MALFORMED`. (2) The determinism check treated exchanges and
  lifecycle events as one sequence space, but an exchange and the event it causes share one
  session sequence, so every real capture was flagged `DUPLICATE_SEQUENCE`. Both fixed in product
  code; the other failures were cascades.
- T-031 first run: 4 of 5 failed. (1) Re-saving an identical mapping collided on the unique
  mapping digest; the digest now binds the import revision, and the replay trial identity uses a
  separate content digest so identical mappings keep one canonical digest. (2) The user-file
  mapping proposal generated duplicate step IDs (`status-2`) when a status read followed a
  provider status; fixed. Remaining failures were cascades.
- T-032 first run: replay fidelity reported MISMATCH because the reused happy-path timeline serves
  PROCESSING before SUCCESS while the user trace saw SUCCESS on its first read. That was correct
  product behavior; the test now edits the mapping. T-033 first run exposed a corpus-diff defect:
  adding a second revision of an existing scenario was reported as a revision change; the pairing
  logic was fixed.
- T-039 first run: two assertions were too strict about unrelated findings (digested signed
  material, which the test trace also carries); test narrowed. T-030 passed on its first run.

## Security and privacy review (module scope)

- Raw source bytes live only in process memory for the call; the journal holds the raw digest,
  byte count, sanitized form (unless rejected), and finding metadata. Secret values are never
  persisted (whole-database scan in T-029); configured secrets are passed in memory only.
- Quarantine analysis imports no network capability (static audit) and made zero network or DNS
  attempts under the tripwire (T-039). The replay trial child receives data only over IPC.
- Signed material (`txHash`) is replaced by its profile digest before persistence.
- Source files avoid literal bidirectional or guillemet characters; escapes are used instead.

## README snippet for the final consolidation stage

```markdown
### Capture-to-regression (M05)

A failing installed-client case can be captured (`captureInstalledCase`), quarantined without
network access, sanitized, mapped to a typed regression, replay-verified in repeated trials
(including a separate process), explicitly reviewed, and promoted into a new immutable scenario
revision and a new corpus revision. Secret-bearing, nondeterministic, unresolved, unreviewed,
replaced, or identity-mismatched traces cannot promote. A regression is complete only after the
corrected build passes the promoted case through the normal proxy/journal/kernel path.
See `docs/adr/0010-trace-quarantine-capture-to-regression.md` and `docs/status/M05.md`.
```
