The sandbox suite compares, at each step, the badge the CLI writes, the decision of
`certificate verify --digest`, and the decision, findings and accepted certificate ids the page
shows: before any certificate (`NO_CERTIFICATE`), a PASS certificate (`CERTIFIED_PASS`, by digest,
by a bundle file chosen in the page, and by project), unknown registry code
(`REGISTRY_CODE_UNKNOWN`), a FAIL certificate from a second attester (`CERTIFIED_FAIL`, and the
project badge following the newest certificate or a pinned attester), that attester revoked
(`ATTESTER_REVOKED`), an unreachable registry and a non-registry account (`UNVERIFIED` only with
`--write-on-error`; otherwise exit 5 or 6 and no file), a link naming a public RPC endpoint
(refused, no request to it), and a link naming a non-registry account.

How the tests were written, plainly: the browser-core test file was written before `browser.ts`
existed, but it was first run after the implementation and passed on that run; the badge, link,
site and sandbox tests were written after or together with their code. "Failing test first" was
observed only in the sandbox suite, whose first run had three failures (an expectation that missed
the `BUNDLE_NOT_CHECKED_LOCALLY` finding of every digest-only check, a request filter that matched
the page URL itself, and the page reporting `VIEW_FAILED` instead of the node's
`CodeDoesNotExist` reason; the last was a real defect in `browser.ts` and is fixed). What stands in
for test-first elsewhere: the page decision is compared with the Node decision on the same inputs,
and with the CLI against a real node.

## README snippet (for the integration stage)

````markdown
## RouteSpec Certified badge

[![RouteSpec Certified](https://img.shields.io/endpoint?url=https%3A%2F%2Fgnanam1990.github.io%2Froutespec-near%2Fbadge%2Ftestnet.json)](https://gnanam1990.github.io/routespec-near/?project=gnanam1990%2Froutespec-near&network=testnet)

The badge shows what the `routespec-registry` contract on NEAR says about this project's newest
release certificate: "certified PASS" only when an attester the registry owner enrolled, and has
not revoked, signed a PASS certificate for exactly that evidence bundle. A certified FAIL is shown
as FAIL; a revoked attester, a missing certificate, or a registry that cannot be read is shown as
such. The `routespec-pages` workflow regenerates it after each certificate run and daily.

Click it to open the verify page. It runs in your browser: choose the evidence bundle file (it is
not uploaded), paste its digest, or name a project. The page computes the SHA-256 itself, reads the
registry over read-only RPC, checks every Ed25519 signature with WebCrypto, and reaches the same
decision as `routespec certificate verify --digest`.

Add a badge to your own project once your certificates are published:

```sh
node --no-warnings packages/cli/bin/routespec.mjs certificate badge \
  --project-key <your project key> --registry <registry account> --network testnet \
  --write-on-error --out badge.json
```

Serve `badge.json` anywhere public and use
`https://img.shields.io/endpoint?url=<url-encoded badge.json URL>` as the badge image.

The badge and the page check a bundle digest; they do not verify the bundle contents
(`certificate verify --bundle` does). Steps: `docs/runbooks/certified-badge.md`. Decisions:
`docs/adr/0031-certified-badge-and-verify-page.md`. Evidence: `docs/status/M49.md`.
````
