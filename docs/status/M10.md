## What was built

- `packages/ci` (`@routespec/ci`, `routespec-ci-action@1.0.0`), bin `routespec-ci`:
  - `context.ts`: trust classification (LOCAL, TRUSTED, UNTRUSTED, PULL_REQUEST, FORK) from the
    runner environment and event payload; `pull_request_target` and unprovable payloads are FORK.
  - `config.ts`: `routespec.ci-config/1`, strict bounded JSON (M05 reader), closed zod schema,
    claim-key scan at every depth, workspace-confined paths (no absolute, traversal, or symlink).
  - `enforcement.ts`: mode resolution capped at `REQUIRED_CHECK_UNVERIFIED`; exit code to
    conclusion mapping (only exit 0 with PASS is `success`).
  - `secrets.ts`: removes provider and CI credentials from the action's own environment before any
    configuration or client code is read; child environments also drop loader/proxy variables.
  - `identity.ts`: artifact/lock/manifest/client/config/toolchain digests from bytes; workspace
    HEAD must equal `GITHUB_SHA`; complete run identity; optional pinned repository/workflow and
    artifact digest.
  - `uploads.ts`: staging with trust rules, database/trace/token/secret/author-path refusal, size
    and retention bounds, and `upload-manifest.json`.
  - `attestation.ts`: records CI attestation as `UNAVAILABLE (HOSTED_ISSUER_CANNOT_BIND_NONCE)`.
  - `action.ts`: the orchestrator (registration through the real `routespec` CLI commands, gate run

    re-render, staging). `outputs.ts`: step outputs and job summary. `sbom.ts`: CycloneDX 1.5.
  - `test/support/sample-client.ts`: the example client launch module (starts the installed

## Real vs simulated vs blocked

- **Real:** the `routespec-ci` process; the real `routespec` CLI commands for every registration;
  `routespec gate run` as its own process through the reviewed launcher; the networkless proxy,
  scenario runtime, kernel, and SQLite journal on real files; a separately launched installed
  subject per case running the pinned official SDK with the RouteSpec adapter; real reports and a
  real evidence bundle; git reading the real checkout; staging on real files.
- **Simulated (labelled):** the GitHub runner — environment variables (`GITHUB_*`, `RUNNER_TEMP`,
  `GITHUB_OUTPUT`, `GITHUB_STEP_SUMMARY`) and the event payload file are written by the test
  harness. Planted credentials are random canaries, not real tokens. The upload itself stops at
  the staging directory.
- **NOT_RUN:** any GitHub-hosted run of `ci.yml` or `routespec-gate.yml`; the T-027/T-009 parity
  regressions on Linux and macOS (only win32 ran, and passes); `actions/upload-artifact`; the
  action SHAs (recorded, not resolved against GitHub).
- **BLOCKED:** CI attestation (`CI_ATTESTED`). GitHub's hosted OIDC issuer has no
  caller-controlled `nonce` claim, so it cannot satisfy the M08 binding, and CI may not enroll a
  principal. Builds therefore stay `USER_ASSERTED_LOCAL`; `requireAttestedBuild` yields REVIEW
  (tested). Unblocking needs an issuer that signs a chosen nonce, or a self-hosted runner with an
  enrolled `LOCAL_LAUNCHER_KEY` launcher and a persistent journal.

## Security and privacy review

- Credentials: provider and CI credentials are deleted from the action's process environment
  before configuration or client code is read; T-058 proves the client module and subject see no
  credential-shaped variable and that no canary reaches stdout, stderr, step outputs, summary,
  journal, reports, or staging, in all five trust contexts.
- Tokens: case and reconciliation tokens cross only the launcher IPC pipe and the in-memory
  handoff object (M06 path, unchanged); staging refuses any `rsct_`/`rsctl_`/`rsprobe_` token.
- Uploads: only one staged directory is uploaded; databases (by name and by SQLite header), the
  journal directory, raw traces (by name and content), secrets, author paths, symlinks, and
  out-of-root paths are refused; retention is 1–30 days.
- Workflows: `contents: read`, no `pull_request_target`, no secret references, inputs via `env:`
  only, `persist-credentials: false`, SHA-pinned third-party actions.
- Enforcement: no verified or blocking state is representable in the action's output types; claim
  keys and flags are refused before anything runs; RouteSpec configures no repository setting.

## Known limits

- Remote CI never ran; the workflow syntax was checked by parsing, not by GitHub.
- The action SHAs are recorded from upstream release tags but were not resolved remotely.
- CI attestation is BLOCKED (see above).
- The client module runs inside the action process (it is integrator code); the action removes
  credentials first, but it does not sandbox that code.
- The gate action does not launch the live-dry adapter in any context (`ELIGIBLE_NOT_RUN` in a
  trusted job); RP-07 stays the M07 operator runbook.
- Upload scanning is pattern- and value-based; it cannot detect an arbitrary unknown secret.

## README snippet for the consolidation stage

```md
### CI (M10)

`routespec-ci run --config routespec.ci.json` runs the gate in CI through the reviewed launcher
and stages only redacted reports for upload (`.github/actions/routespec-gate`, example workflows
in `.github/workflows/` and `docs/ci/`). It exits 0 only for a PASS decision; REVIEW and NOT_RUN
are never success. Enforcement is `CI_CHECK` or `REQUIRED_CHECK_UNVERIFIED`, always unverified
and never blocking. Pull-request and fork jobs get no provider secrets, cannot start the live-dry
adapter, and can upload only the JSON/JUnit/SARIF reports. CI attestation is unavailable with the
hosted GitHub issuer, so CI builds stay `USER_ASSERTED_LOCAL`. Remote CI runs: NOT_RUN.
```
