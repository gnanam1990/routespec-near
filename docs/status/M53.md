The three patterns:

| Pattern                            | Rule                                                                                                            | Linked codes                                                                                                                                                                |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RECONCILE_THROUGH_STATUS`         | An unanswered deposit submission is outcome-unknown: read the status of the same deposit address until terminal | `INV03_SECOND_MUTATION_UNDER_UNCERTAINTY`, `INV03_RECONCILIATION_INCOMPLETE`, `INV03_RETRY_JOINED_BEFORE_FENCE`, `INV05_OUTCOME_UNDETERMINED`, `INV06_TERMINAL_NOT_REACHED` |
| `IDEMPOTENCY_KEY`                  | One key, one quote, one deposit address per order; a retry reuses them                                          | `INV02_BINDING_INCONSISTENT`, `INV03_SECOND_MUTATION_UNDER_UNCERTAINTY`, `INV03_RETRY_JOINED_BEFORE_FENCE`, `INV07_EVIDENCE_REUSED`                                         |
| `NO_SECOND_ORDER_WHILE_UNANSWERED` | No fresh quote and no second deposit while the first submission has no answer                                   | `INV03_SECOND_MUTATION_UNDER_UNCERTAINTY`                                                                                                                                   |

Codes about RouteSpec's harness, evidence, or configuration (for example `INV04_DECLARED_HOOKS_ONLY`,
`INV05_LEG_MISSING`, `INV08_REQUIRED_EVIDENCE_WEAK`) link no pattern and keep their remediation.

What the CLI test does, all for real:

1. The hedging build on `slow-commit-answer` is **FAIL** (exit 2). The advice links INV-03
   `INV03_SECOND_MUTATION_UNDER_UNCERTAINTY` to "No second order while the first is unanswered",
   "Reconcile through status" and "One idempotency key per order", and finds the order-key change,
   the second `getQuote` and the second `submitDepositTx` at their real lines. SARIF carries one
   result per shape at that line; without `--source` it still has none.
2. The suggested diff is applied with `git apply`, installed as a new build, and gated on
   `slow-commit-settles`: **PASS** (exit 0). The unpatched build on that variant is REVIEW
   (its hedge quote is refused, the case aborts).
3. The naive build on `accepted-then-lost-response` is **REVIEW** (exit 3): INV-03
   `INV03_RECONCILIATION_INCOMPLETE` links "Reconcile through status"; the resubmit loop and the
   missing status read on the error path are found. Its patched build on the same scenario:
   **PASS** (exit 0).
4. `gate evaluate` and `gate show` on the stored evaluation give advice with the same digest.

`slow-commit-settles` is a test-owned synthetic variant of the delivery scenario without the
fresh quote and second deposit steps. In `slow-commit-answer` the status only progresses after a
second order, so a client that never places one (the reconciling build included) cannot reach a
terminal status there; the patched hedging build is therefore gated on the variant.

A first full `pnpm run check` failed T-025 (3 cases) and T-057 (1 case): the CLI imported the
TypeScript compiler at every start, and the extra start-up time broke those kill-timing tests.
The CLI now imports the fix-pattern module only when advice is asked for. Later full runs while
other suites loaded this machine still failed the same T-025 and T-057 cases; a full `pnpm run test`
on an unchanged `main` checkout failed the same cases at the same time (6 failed), and the final
run above, on the merge candidate, was green.

## README snippet (for the README owner)

```md
### Fix patterns

On FAIL or REVIEW, RouteSpec tells you what to change in your client. Add
`--fix-md fix.md --source src/client.ts` to `routespec gate run` (or `gate evaluate`, `gate show`):
each violated invariant is linked to a code pattern (reconcile through status, one idempotency key
per order, no second order while the first is unanswered), the official 1Click SDK calls in your
file are listed with their lines, and a suggested diff is written against them. The advice is
advisory: it never changes the verdict. Apply the diff, rerun the gate, and the new verdict is the
one that counts. `routespec fix patterns` lists the patterns. Example:
[docs/demo/m53-fix-advice-hedging.md](docs/demo/m53-fix-advice-hedging.md).
```
