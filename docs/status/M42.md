## Finding: why the first probe was `INCOMPATIBLE`

The owner's first run (2026-11-13) received HTTP 201 in 674 ms and RouteSpec classified it
`INCOMPATIBLE` / `RS_FINALIZATION_REQUEST_MISMATCH` / `SHAPE_INCOMPATIBLE`. The comparison was a
byte-level digest equality between the request sent and the `quoteRequest` the endpoint echoes.
A redacted field-level diff (new `--debug-echo-diff` option, one extra dry call) showed that every
field we sent was echoed unchanged except for documented provider normalisation:

| Field                | Change            | Sent                   | Echoed                                                                |
| -------------------- | ----------------- | ---------------------- | --------------------------------------------------------------------- |
| `deadline`           | CHANGED           | `dddd-dd-ddTdd:dd:ddZ` | `dddd-dd-ddTdd:dd:dd.dddZ`, **same instant**                          |
| `depositMode`        | ADDED_BY_PROVIDER | absent                 | `SIMPLE` (documented default)                                         |
| `confidentiality`    | ADDED_BY_PROVIDER | absent                 | `public` (documented default)                                         |
| `quoteWaitingTimeMs` | ADDED_BY_PROVIDER | absent                 | `0` (documented default)                                              |
| `insured`            | ADDED_BY_PROVIDER | absent                 | `false` (documented default)                                          |
| `appFees`            | ADDED_BY_PROVIDER | absent                 | one entry, `fee: 20`, recipient a 64-hex account that we did not send |

The 1Click fee documentation says that an authenticated request that omits `appFees` is charged
20 bps by 1Click (1 bp on stablecoin and same-asset routes; 25 bps without an API key); the echo
makes that fee explicit as an `appFees` entry with a provider recipient. The request-known fields
`amount`, `originAsset`, `destinationAsset`, `recipient`, `refundTo`, `dry`, `swapType`,
`slippageTolerance`, and the three `*Type` fields were all echoed unchanged.

Root cause: a RouteSpec comparison defect. The profile treated the echo as byte-identical
request material, so the endpoint's documented normalisation was reported as a mismatch. The
official API is compatible with the pinned 0.1.26 SDK profile.

## Fix (profile `oneclick-v0@1.0.0`, comparison only)

`validateQuoteFinalization` now accepts an echo as equivalent only when:

1. every field the client sent is echoed unchanged; `deadline` may differ only in ISO-8601 text
   for the same instant (millisecond precision; anything finer must match exactly);
2. no sent field is dropped;
3. an omitted optional field may be added only with its documented default
   (`depositMode: SIMPLE`, `confidentiality: public`, `quoteWaitingTimeMs: 0`, `insured: false`);
4. an omitted `appFees` may be added only as exactly one provider fee entry of 1, 20, or 25 bps;
5. any other added field (`referral`, `rebates`, `sessionId`, `connectedWallets`,
   `virtualChain*`, `customRecipientMsg`) or non-default value is a mismatch.

The provider-defaulted values are response-assigned and are bound into the finalization as
`extensions.providerDefaultedRequestFields` (so a different provider fee recipient is a different
finalization digest). The bound `quoteRequestDigest` is still the digest of what was sent. The
rules are validation logic (`ECHO_DOCUMENTED_DEFAULTS`, `ECHO_PROVIDER_DEFAULT_FEE_BPS`,
`equivalentEcho` in `packages/contracts/src/protocol/oneclick-v0.ts`); the profile's field sets,
routes and statuses are unchanged, so the profile integrity digest stays
`sha256:71e0c45dc0c4dbb775ff4271c78ddc17bfa56c1402654fd4c685deb52f4e3d05` and no golden replay
vector moves. (An intermediate revision that also published the rules inside the digested profile
body was dropped because it changed the T-009/T-013 golden vectors; run 3 below used it.)

The debug option `--debug-echo-diff` prints, only on an echo mismatch, field names and value
classes (enum, boolean, and integer values as-is; date-times as a digit pattern plus whether the
instant matches; strings as "same as the sent recipient/refundTo" or a coarse kind such as
`NEAR_IMPLICIT_HEX64`). It never carries an address value, signature, correlation ID or amount
out, and it is never written to the ledger.
