# M47A — Registry contract audit: status evidence

- Scope: the `routespec-registry` contract merged in M47 (`contracts/routespec-registry`), the
  TypeScript verifier and NEAR client (`packages/registry`), and its callers
  (`packages/cli/src/certificate.ts`, `packages/ci/src/certificate.ts`). Scoped run, standard
  profile, source review plus local tests only. Nothing was deployed and no testnet or mainnet
  transaction was sent.
- Base: `main` at `4fe98d1`. Branch: `feat/routespec-m47a-registry-audit-fixes`.
- The contract holds no funds and moves none: no payable method, no promise, no cross-contract
  call, no callback, no token standard. The fund-handling attack classes (NEP-141 receivers and
  callback ordering, promise failure and rollback, reentrancy across callbacks, `ft_on_transfer`
  return values, storage-deposit and payee registration, token-id confusion, decimals, rounding,
  ledger conservation, gas exhaustion in callbacks, unexpected assets) were checked and do not
  apply: the wasm imports no `promise_*` or balance host function and every method refuses an
  attached deposit (both asserted by the sandbox suite).

## Findings

| Id     | Severity | Status        | Title                                                                     |
| ------ | -------- | ------------- | ------------------------------------------------------------------------- |
| M47A-1 | low      | FIXED         | A small-order Ed25519 attester key lets anyone forge certificates         |
| M47A-2 | low      | ACCEPTED_RISK | Certificate storage is paid by the registry account, not by the publisher |
| M47A-3 | info     | ACCEPTED_RISK | Project keys are not bound to an attester                                 |
| M47A-4 | info     | ACCEPTED_RISK | The signed payload names the registry account, not the chain              |

### M47A-1: small-order attester keys (FIXED)

`enrol_attester` accepted any 32-byte Ed25519 public key. For a key that encodes a point of small
order (for example the identity point, `ed25519:4uQeVj5tqViQh7yWWGStvkEG1Zmhx6uasJtWCJziofM`),
the signature `R = key, s = 0` verifies for every message under cofactorless verification, which
is what NEAR's `ed25519_verify` and Node's `crypto.verify` do. If such a key was ever enrolled
(by mistake, or because an attester applicant handed it over), any account could publish a
certificate with any verdict for any bundle and project under that attester, and
`certificate verify` would accept it, also with the key pinned through `--attester`.

Failing tests first, on the unchanged code:

- sandbox (real local node): the identity key and six other small-order encodings were enrolled,
  and a stranger with no key published a forged certificate (`ACCEPTED`, certificate count 1);
- `aggregateRelease` returned `PASS` for the forged certificate with the key enrolled and pinned;
- `certificate verify --attester <identity key>` went on to contact the endpoint (exit 5);
- Node accepts the forged signature (kept as an assertion in `keys.test.ts`).

Fix: `routespec-certificate::is_small_order_key` and its TypeScript twin `isSmallOrderPublicKey`
recognise the seven encodings (either sign bit) of the eight small-order points, the list
libsodium blocks; each was checked independently to have order dividing 8. The contract refuses
such a key at enrolment with `RSREG_KEY_WEAK`; `verifyEd25519` treats every signature for one as
invalid; the CLI refuses one as an `--attester` pin (exit 4).

### M47A-2: storage paid by the registry (ACCEPTED_RISK, recorded in ADR-0029)

`publish` takes no deposit, so the registry account pays the storage of every certificate (well
under 0.01 NEAR each). Only a holder of an enrolled attester key can cause writes, one per bundle
digest, so a compromised or misbehaving attester key could lock the registry balance and stop
publication for every attester until the owner revokes the key and adds balance. A compromised
attester key can already sign false certificates, which is worse; the owner's response is the
same (revoke). Keep the registry balance small, enrol only keys you control, and watch the
`certificates` count of each attester (`list_attesters`).

### M47A-3: project keys are not bound to an attester (ACCEPTED_RISK)

Any enrolled attester may publish under any project key. A verifier that does not pin attester
keys therefore trusts every enrolled attester for every project. This is the documented default
of `certificate verify`; pin `--attester` for a release decision that matters.

### M47A-4: the payload binds the registry account, not the chain (ACCEPTED_RISK)

A signature is valid only for one registry account id. An account id that exists on both
networks under the same holder (an implicit account, or the same top-level name) would accept
the same envelope on both, if the same attester key is enrolled on both. The statement stays
true (the attester signed exactly those values); use different attester keys for testnet and
mainnet.

Also checked, nothing found: owner checks on `enrol_attester` and `revoke_attester`;
`#[init] #[private]` initialisation (only the contract account, once); no upgrade or owner
transfer method (redeployment is the account holder's decision, ADR-0029); storage prefixes
cannot collide; replay (one certificate per attester and bundle, a timestamp window, and the
registry account in the payload); every field has a closed character set, so the event log
cannot be broken out of; views are bounded (64 attesters, 8 certificates per bundle, pages of
50); overflow checks are on in the release profile; key text from the RPC must be canonical;
signatures are re-verified locally; `--network` checks the chain id; secrets stay out of the
gate step.
