## T-036 container-host attempts (real, Docker Engine in WSL 2)

Listeners on this host (all loopback): control service on 127.0.0.1 serving the built console,
control service on ::1, scenario proxy (both on configured ports in 9350-9399), the canary
interceptor sink bound to a running case, and the live-dry adapter (OS-assigned loopback ports).
Each was first reached on its own loopback from this host (sanity), and the console answered
`GET /` with its HTML. Per container, the results by attempt category (counts; no addresses):

| Category (attempts per container)                                                                                              | Bridge container          | Host-network container       | Confined subject                            |
| ------------------------------------------------------------------------------------------------------------------------------ | ------------------------- | ---------------------------- | ------------------------------------------- |
| listener at this host's addresses (10: 5 ports x 2 addresses)                                                                  | TIMEOUT 10                | TIMEOUT 10                   | ENETUNREACH 10                              |
| listener at the engine host's addresses (15: 5 ports x 3; the bridge and default gateways coincide with these and this host's) | ECONNREFUSED 15           | ECONNREFUSED 15              | ENETUNREACH 15                              |
| listener at the container's own loopback (15)                                                                                  | ECONNREFUSED 15           | ECONNREFUSED 15              | CONNECTED 4 (tunnels only), ECONNREFUSED 11 |
| listener by host name (15)                                                                                                     | ENOTFOUND 10, TIMEOUT 5   | ENOTFOUND 10, ECONNREFUSED 5 | EAI_AGAIN 15                                |
| DNS names (3)                                                                                                                  | ENOTFOUND 2, RESOLVED 1   | ENOTFOUND 2, RESOLVED 1      | EAI_AGAIN 3                                 |
| engine API ports 2375/2376 (10)                                                                                                | ECONNREFUSED 6, TIMEOUT 4 | ECONNREFUSED 6, TIMEOUT 4    | ENETUNREACH 10                              |
| engine sockets (3)                                                                                                             | ENOENT 3                  | ENOENT 3                     | ENOENT 3                                    |
| WSL paths `/run/WSL`, `/mnt/wsl`, `/init`, `/mnt/c/Windows/System32`                                                           | ABSENT 4                  | ABSENT 4                     | ABSENT 4                                    |
| Windows executable from the checkout (`esbuild.exe --version`)                                                                 | EXIT_1, vsock denied      | EXIT_1, vsock denied         | EXIT_1, vsock denied                        |
| control listener on the engine host's network (positive control, 2)                                                            | **CONNECTED 2**           | **CONNECTED 2**              | ENETUNREACH 2                               |

- **No container reached any RouteSpec listener.** Ordinary containers can reach the engine
  host's network (the control listener answered), but this host's addresses time out (WSL Hyper-V
  firewall) and the engine host's own addresses and loopback have nothing on RouteSpec's ports
  (WSL is in `nat` mode, so its loopback is not this host's loopback).
- **The confined subject has no route out.** It was `PROCESS_TREE_ENFORCED` with no findings
  (self-observation: uid 1000, `Seccomp: 2`, only `lo`). Its only connections were the proxy and
  sink tunnel endpoints on its own loopback (127.0.0.1 and `localhost`). The launcher's tunnel
  counters equalled those 4 connections plus the HTTP request, which the real proxy answered with
  a RouteSpec error code. Everything else reported no route; nothing timed out.
- **Windows interop through WSL binfmt.** In every container the kernel started WSL's `/init` for
  the Windows executable (flag `F`), which failed on `UtilBindVsockAnyPort` (EPERM from the
  default seccomp filter). No Windows program output appeared. A manual run with
  `seccomp=unconfined` passed the vsock step and still produced no Windows program output (no
  interop socket in the container). Seccomp is therefore one of two layers here, and the launcher
  now requires it in the self-observation (ADR-0020 §4).

## Real vs simulated vs blocked

- **Real:** every container attempt above, against the real engine. The listeners were the real
  product components. The registry queries (`pnpm audit`, `npm view`) were read-only. The
  dependency change was installed from the public registry.
- **Simulated (by design):** provider behaviour behind the scenario proxy (networkless SIMULATE
  runtime). The interceptor's no-effect canary sink. The probe is a hostile test subject, not the
  official client.
- **NOT_RUN:** WSL `mirrored` networking mode, plain Linux Docker, rootless or user-namespaced
  engines, Linux and macOS hosts, and an independent security review. Gate impact: the RP-06 gap
  "container-host access part of T-036 NOT*RUN" is closed on this host. The remaining
  `WORKING_LOCAL` requirements (real CI run RP-05, capture refusal RP-08, interceptor profile
  review) are unchanged by M17. \*\*No `WORKING*\*` level is claimed.\*\*
